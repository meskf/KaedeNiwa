## 1. 项目概述

### 1.1 定位

KaedeNiwa v2 是对旧版（C++20 + React 19 + Electron）的完全重写。目标：

- Rust 全栈 workspace（服务器 + 客户端 + UI + 采集）
- MLS (RFC 9420) 单一化密钥体系，服务器无法解密
- Dioxus 跨平台 UI（Web WASM  Desktop Wry）
- 4K608K60 屏幕共享 + 系统音频捕获 + 一起听歌
- LiveKit SFU 媒体中继 + 内建 E2EE

### 1.2 核心原则

1. 服务器零解密：`kaede-server` 只依赖 `kaede-protocol`，转发的 `Mls` payload 是不透明字节流
2. 密钥从 MLS 派生：所有对称密钥从 MLS `export_secret` 派生（S1S2 已废弃）
3. 实时媒体用 LiveKit E2EE（v2.1 起），SFrame 保留给离线落盘场景
4. 事件驱动：UI 通过 `events()` 订阅，不轮询；`events()` 是 fanout（多订阅者各拿全部）

### 1.3 Crate 分层（12 个）

按变更频率划分。重构时优先动下层，稳定层尽量不动。

 层  Crate  职责  测试 
------------
 稳定  `kaede-protocol`  线协议类型（CBOR）  13 
 稳定  `kaede-crypto`  AEAD  HKDF  X25519  ML-KEM  SFrame 原语  31+1 
 演进  `kaede-mls`  openmls 0.9.1 封装 + snapshot cipher  27 
 演进  `kaede-storage`  存储 enum（memory  sqlite  IndexedDB）  5 
 演进  `kaede-client`  状态机 + HTTP + WS + RoomSession  41+2 
 演进  `kaede-media`  媒体会话层（MediaSession  AudioSession  LiveKit）  6 
 易变  `kaede-server`  axum HTTP + WebSocket + SQLite  5 e2e 
 易变  `kaede-ui`  Dioxus 组件（占位，将重做）  0 
 入口  `kaede-wasm`  Web 入口  0 
 入口  `kaede-desktop`  Desktop 入口（Wry）  0 
 附加  `kaede-capture`  屏幕采集 + NVENC + 音频（GStreamer）  0 
 附加  `kaede-livekit-spike`  LiveKit API 验证（实验）  0 

已移除：`kaede-encode`（空壳）、`kaede-stream`（被 `kaede-media` 取代）。

4. 密钥体系
4.1 总体原则
S1  S2 废弃

服务器不持有 crypto_root_hex

所有密钥从 MLS export_secret 派生

文本走 MLS Application Message

实时媒体走 LiveKit E2EE（AES-GCM）

离线媒体走 SFrame（key 从 MLS exporter 派生）

4.2 SFrame key 派生
单一 channel 的所有媒体流原本共用同一 SFrame key，导致 AES-GCM nonce 复用。现已两层隔离：

1. Purpose 分离 —— 音频  视频  屏幕  文件各自独立 key

text
exporter context = channel_id  0x00  purpose
purpose ∈ {default, text, voice-audio, voice-video,
           screen-video, screen-audio, file}
2. Sender 分区 —— 同一 channel 多 sender 共用 key 时，counter 高 32 位是 sender_id，低 32 位是帧序号

text
sender_id = SHA256(uid)[0..4]        （跨设备一致）
counter  = (sender_id as u64)  32  seq
两条修复合起来，保证同一 epoch 内 (key, nonce) 永不复用。

4.3 SFrame 帧格式（与 v1 逐字节对齐）
text
[ key_id    4 BE ]
[ counter   8 BE ]
[ payload   AES-256-GCM(ct  16-byte tag) ]
Nonce：[0,0,0,0]  counter(8B BE)

AAD：12 字节帧头（key_id  counter）—— 篡改 key_idcounter 会导致 GCM tag 校验失败

KAT 锚定 v1（kaede-cryptosrcsframe.rsprint_kat）

4.4 E2EE 共享 key（LiveKit，v2.1）
apilivekite2ee-key 确定性派生：

text
key = HMAC-SHA256(LIVEKIT_API_SECRET, kaede-e2ee-v1  channel_id)
同一 channel_id → 同一 key，房间内所有成员一致

不同 channel_id → 不同 key

server 无需存储状态

实现：kaede-serversrclivekit.rsderive_e2ee_key

client API：RoomSessionget_livekit_e2ee_key(channel_id)

历史 bug（2026-10-16 修）：原实现每次调用 randthread_rng().fill_bytes() 生成新 key，房间内成员拿到不同 key，永远解不开。

4.5 MediaMeta 侧信道
媒体格式元数据（采样率  声道  codec）不走 SFrame 帧头，走 MLS Application Message：

text
MediaMetaPayload { kind media_meta, channel_id, uid,
                   purpose, codec, key_id, sender_id,
                   sample_rate, channels, action }
接收端从 ClientEventMediaMetaReceived 拿。SFrame 帧格式不变。

4.6 MLS 签名密钥
不用 openmls_basic_credential（依赖 openmls_traits 0.4，与 openmls 0.9.1 的 0.6 冲突）。

自己在 kaede-mlssrcidentity.rs 实现 40 行的 SignatureKeyPair。

4.7 Snapshot cipher
KaedeMlsProvider 的 snapshot 用 AES-256-GCM 加密

Key 从设备标识派生（SHA256(kaede-snapshot-v1 + uid +  + server_url)）

TODO：接 OS keystore（DPAPI  Keychain  WebCrypto），见 TD-3

4.8 媒体加密密钥边界
UI 只调 RoomSessionexport__key(channel)，不直接碰 MLS：

text
RoomSessionexport_voice_audio_key(ch) - [u8; 32]
RoomSessionexport_voice_video_key(ch) - [u8; 32]
RoomSessionexport_screen_video_key(ch) - [u8; 32]

7. 媒体层
7.1 设计原则
UI 不感知平台差异：只看到 MediaSession  AudioSession  LiveKit，不关心 Web  Native

8.5 视频显示（I420）
rust
use livekitprelude;
use livekitwebrtcvideo_streamnativeNativeVideoStream;
use kaede_mediaLiveKitVideoSink;

let sink = LiveKitVideoSinknew();
let mut stream = NativeVideoStreamnew(video.rtc_track());

while let Some(frame) = stream.next().await {
    let buf = frame.buffer.as_ref();
    let (w, h) = (buf.width(), buf.height());
    let i420 = buf.to_i420();
    let (y, u, v) = i420.data();
    let mut packed = Vecwith_capacity(y.len() + u.len() + v.len());
    packed.extend_from_slice(y);
    packed.extend_from_slice(u);
    packed.extend_from_slice(v);
    sink.push_i420(&packed, w, h, frame.timestamp_us  1000);
}
I420 而非 RGB：libwebrtc 的 VideoFormatType 命名与 GStreamer caps 字节序约定不一致，实测 BGRARGBA 均偏色（紫红）。I420 无字节序歧义，且带宽更小（12 vs 32 bitpixel）。

管线做 1280x720 缩放，避免 2560x1440 BGRA 撑爆 PCIe 带宽

9. 状态管理
注：kaede-ui 是占位实现，将完全重做。本文档描述的原则（use_signal vs use_store）在新 UI 中仍然有效，但具体组件结构会变。

9.1 Dioxus 0.7 的两种原语
use_signal —— 原子值
rust
let mut count = use_signal( 0);
let value = count.read();
count.set(value + 1);
用于：backend_status  signaling_state  profile（单对象） 当前选中频道 ID  UI 开关  临时表单状态。

use_store —— 嵌套集合，路径级响应式
rust
#[derive(Store, Default)]
struct AccountsState {
    accounts HashMapServerId, ServerAccount,
    current OptionServerId,
}
用于：accounts（多服务器） peer_pubkeys  messages_by_channel  频道树  成员列表。

不使用 use_state
Dioxus 0.7 明确 use_state 已被 use_signal 取代。

9.2 路径级响应式示例
rust
#[derive(Store, Default)]
struct AppState {
    crypto CryptoState,
    messages MessageState,
    ui UiState,
}

#[derive(Store, Default)]
struct CryptoState { epoch u64, peer_keys HashMapUserId, PeerKey }

#[derive(Store, Default)]
struct MessageState { by_channel HashMapChannelId, VecMessage }

2026-10-15 SFrame nonce 复用修复
问题：

同一 channel 的音频视频屏幕共享共用同一 SFrame key
同一 channel 的多个 sender 各自从 counter=0 开始加密
两处叠加 → AES-GCM nonce 复用
修复：

exporter context 加 purpose → 音频视频屏幕文件独立 key
counter 高 32 位 = sender_id（SHA256(uid)[0..4]）→ 多 sender 空间不重叠
顺带把 sframe.rs 里半成品设计落地（原注释说高 32 位是发送者分区，代码没实现）
测试：kaede-mls +5，kaede-crypto +3，kaede-client +2

验证：全 workspace 123 tests passed

2026-10-15 媒体层 stop() hang 修复
问题：MediaSession  AudioSessionstop() 设 flag 后 join 采集线程，但采集线程卡在 rx.recv()，flag 永远读不到 → UI 卡死。

修复：

主循环改用带 200ms 超时的 next_frame_timeout  next_audio_timeout
超时后 continue，回循环头检查 stop_flag
stop() 加 2s 上限（防 pipeline 崩溃）
测试：2 个卡死源回归测试

2026-10-15 删除 kaede-stream
问题：kaede-stream 是 kaede-media 的历史前身，只有 143 行、无单元测试、无其它 crate 依赖。

结论：删除。功能被 kaede-media 的超集覆盖。

2026-10-16 LiveKit E2EE 单一化，去 SFrame 双层冗余
背景：v2.0 媒体路径 = SFrame 加密 → LiveKitSink 解密 → LiveKit E2EE 再加密。两层加密冗余，且 LiveKit 预编码路径无法直接吃 SFrame 密文。

决策：

实时媒体走 LiveKit 内建 E2EE（AES-GCM），不叠加 SFrame
LiveKitSink 重写为 LiveKitPusher + LiveKitSession（视频） LiveKitAudioPusher + LiveKitAudioSession（音频）
MediaSession  AudioSession（SFrame 路径）保留给文件落盘、离线、自建 SFU
顺带修的：

P2：close() 空操作 → 新 LiveKitPusherclose() 有明确语义

P3：unbounded mpsc → async_channel(8) + try_send 满则丢帧

P6：LiveKitConfigwith_e2ee(&str) 保留；新增 with_e2ee_key(Vecu8) 吃 raw bytes

2026-10-16 apilivekite2ee-key 确定性派生
问题：原实现每次调用 randthread_rng().fill_bytes() 生成新 key。房间内 alice  bob 各调一次拿到不同 key，互相解不开。

修复：HMAC-SHA256(LIVEKIT_API_SECRET, kaede-e2ee-v1  channel_id)

server 无需存储状态

请求体加 channel_id

client API 改为 get_e2ee_key(channel_id)

替代方案（未采纳）：

HashMapchannel_id, key 缓存：需 AppState 增加可变状态

从 MLS exporter 派生：不可行，server 不解密 MLS

未来移动端 4G 首屏  3s

16.2 Profile
根 Cargo.toml 有两个 release profile：

toml
[profile.release]
opt-level       = 3
lto             = thin
codegen-units   = 1
panic           = abort
strip           = true
overflow-checks = false

[profile.release-wasm]
inherits      = release
opt-level     = z
lto           = fat
codegen-units = 1
panic         = abort
strip         = true
用途：

cargo build --release → 用 release（Server  Desktop）

cargo build --profile release-wasm → 用 release-wasm（Web）

dx build --release → 由 dx 选择

16.3 关键优化项
优化	影响
opt-level = z	优先体积，速度略降
lto = fat	跨 crate 内联，体积下降
codegen-units = 1	更好的 LTO，编译慢
panic = abort	去掉 unwinding，约 -30%
strip = true	去掉符号表
overflow-checks = false	去掉整数溢出检查
参考数据：2.80 MB → 1.68 MB（-39.9%）

16.4 wasm-opt
Dioxus CLI 自动调用 wasm-opt。手工构建时：

powershell
wasm-opt -Oz ^
  --enable-bulk-memory ^
  --enable-nontrapping-float-to-int ^
  --enable-sign-ext ^
  input.wasm -o output.wasm
三项 --enable- 是现代 WASM 特性，缺失会导致 wasm-validator 报错。

16.5 WASM-Split
Dioxus 0.7 支持代码分割和懒加载：

主 bundle 只包含 UI 骨架和路由

MLS 相关代码放在独立 chunk

用户进入加密房间时按需加载

在 Cargo.toml 的 [package.metadata.dioxus] 下配置（阶段 2 引入）。
