## 0. 总体结论

协议层、密码学原语、服务器鉴权/校验的代码质量较高，之前多轮审计留下的加固点基本到位。
但**核心可用性链路（聊天历史、断线重连、多人语音、私聊/私密频道初始化、附件）存在多处会直接导致功能失效的问题**，其中 2 个是密码学级别的问题：

1. **MLS 状态只在少数几个时间点落盘**，发送消息/处理提交后不保存 → 重启后发送者 ratchet 回退 → 同 generation 的密钥与 nonce 被复用；同时其他人无法再解密。
2. **聊天历史用“一次性”的 MLS Application Message 解密**，导致自己的消息永远读不出、跨 epoch 消息读不出、同一消息第二次读取被当作重放拒绝。

这两点已用可复现探针确认（见附录 A）。

## 1. P0 — 必须修复（核心功能失效 / 密码学风险）

### P0-1 MLS 状态未在发送消息 / 处理 commit 后持久化 → nonce 复用 + 重启后失联

**位置**
- 快照保存点：`crates/kaede-client/src/room.rs:351-362`（become_host/guest）、`:423-425`（host_add_peer）、`:891-893`（踢人）
- 发送路径均不保存：`room.rs:965-991`、`:999-1036`、`:1118-1153`
- 事件循环只 flush DM/channel 快照，不保存主群：`crates/kaede-client/src/connection.rs:1434-1470`（`:1446` 只调用 `flush_dirty_snapshots`）
- 处理 `MlsCommit` 只改内存：`connection.rs:1110-1130`

**已证实的行为（探针）**

对同一个群：在“刚建群”时保存 snapshot → 发送 m1、m2 → 从旧 snapshot 恢复 → 再发送 m3：

```
PROBE bob m1 = true
PROBE bob m2 = true
PROBE bob m3 = Err(... SecretTreeError(SecretReuseError))
```

即恢复后发送端的 generation 回到 0，**用与 m1 相同的密钥/nonce 加密 m3**。服务器同时持有 m1 和 m3 的密文，可 XOR 恢复明文；接收端则因 `SecretReuseError` 拒绝 m3。

**影响**
- 密码学：MLS 层的 AES-GCM key/nonce 复用（比 SFrame 层更严重，因为服务器直接持有两条密文）。
- 可用性：重启后主群状态过期，无法处理新 commit；自己发出的新消息别人解不开；别人 epoch 前进后自己的状态永远落后。

**修复建议**
- 在以下时机 debounce 落盘（例如 100–300ms 合并写）：
  - 每次 `create_message` 成功后；
  - 每次 `process_handshake` / `merge_staged_commit` 后（epoch 或 ratchet 变化）；
  - `begin_media_session` 的 `self_update` 后。
- 更稳妥：保存时记录 `epoch + generation`，恢复时若磁盘状态比内存旧则拒绝发送并提示“需重新加入”。
- 长期建议把 MLS provider 换成真正的事务型存储（openmls 支持自定义 `StorageProvider`），避免“整包快照”这个根本性脆弱点。

### P0-2 聊天历史不可恢复（自己的消息 / 跨 epoch / 二次读取）

**位置**
- `crates/kaede-client/src/room.rs:638-695`（`load_history` 逐条 `mls_decrypt`）
- `crates/kaede-client/src/room.rs:594-635`（`load_history_before`）
- `crates/kaede-client/src/connection.rs:324-330`（`mls_decrypt` → `decrypt_app`）
- `crates/kaede-mls/src/group.rs:25-28`：`MlsGroupCreateConfig` 未配置 `max_past_epochs`（openmls 默认 0）

**已证实的行为（探针）**

```
PROBE own-decrypt      = "not an application message"       // OwnPrivateMessage
PROBE cross-epoch      = TooDistantInThePast                 // 成员变更/语音 self_update 后旧 epoch 消息
PROBE first decrypt    = ok
PROBE second decrypt   = SecretReuseError                    // 同一密文第二次解密被当重放
```

**影响**
- 刷新/重启后**看不到自己发过的任何消息**（服务器不回声给自己，历史里又解不开）。
- 只要发生过一次成员加入/踢人/进入语音，**该 epoch 之前的全部频道历史都读不出来**。
- 同一会话内重复拉取同一批历史（如切换频道、分页边界）会得到空列表。
- `content.rs:108-155` 在“消息为空”时会再次拉取；若解密永久失败，存在反复请求的风险。

**修复建议（按推荐度）**
1. **不要把“可回放历史”建立在 MLS Application Message 上**。改为像私密频道那样使用 per-channel 静态密钥（`MLS exporter` + 随机 nonce，如 `dm_cipher`），历史可重复解密；聊天成员变更时轮换 key 并保留旧 key 版本号。
2. 或者本地持久化明文/自己发出的消息（SQLite/IndexedDB），服务器历史只作为补充。
3. 若坚持 MLS：配置 `max_past_epochs`（牺牲前向保密）并禁止对同一密文二次解密；同时用 `OwnPrivateMessage` 无法解决“自己的历史”问题，仍必须本地存。

### P0-3 同账号第二条连接无法“顶替”旧连接（与 SECURITY.md 声明不符）

**位置**
- `crates/kaede-server/src/ws.rs:377-384`：`Join` 只要 `peer_uids()` 里已有该 uid 就直接回 `Joined` 并 return，永远走不到 `add_peer` 的“踢掉旧连接”逻辑。
- `crates/kaede-server/src/state.rs:121-134`：`add_peer` 才是真正顶替 + 发送 `Kicked` 的地方。

**已证实的行为（探针）**

同一账号建立两条 WS：
```
PROBE first join  = Joined { peers: [] }
PROBE second join = Joined { peers: [] }
PROBE a got commit? = PresenceUpdated(...)   // 没收到 B 的 MlsCommit
PROBE b got error?  = None                   // 服务器把 ensure_joined 错误静默吞掉了
```
B 连接看起来“加入成功”，实际上 `session_id` 仍是 0，之后所有需要 joined 的消息都会被服务器内部报错丢弃（只写日志），客户端完全不知道。

**影响**
- 断线重连时旧连接尚未被服务器判定断开（半开连接、弱网）→ 新连接变“僵尸”，直到旧连接 5 分钟 idle 超时才恢复。
- 多设备/重复登录的安全语义（后登踢前登）实际未实现。

**修复建议**
- `Join` 幂等判断必须带 `session_id`：只有“同一个连接重复 Join”才早退；不同连接应调用 `add_peer` 顶替并给旧连接发 `Kicked`。
- `handle_message` 的 `ensure_joined` 失败应以 `Error{code: NotJoined}` 回给客户端，而不是只 `tracing::warn!`。

### P0-4 多人语音 E2EE key 必然不一致

**位置**
- `crates/kaede-client/src/room.rs:1304-1356`：每个客户端进入媒体会话都执行 `mls_self_update()` 使 epoch 前进，然后**立即**用当前 epoch 派生 key。
- `crates/kaede-ui/src/sidebar.rs:1187-1201`：key 在 `NativeHandle::connect` 时一次性写入 LiveKit KeyProvider。
- `crates/kaede-client/src/connection.rs:1110-1130`：收到别人的 commit 只更新 MLS，不重新派生/更新 LiveKit key。

**影响**
- A 先进语音得到 epoch N 的 key；B 后进触发 epoch N+1，得到 N+1 的 key。A 即使收到 B 的 commit 前进了 epoch，LiveKit 仍在用 N 的 key → 两人互相听不到。
- 人数越多、进入时间越分散，越必然失败。当前实现只有“单人语音”可用。
- DM/私密频道语音则走 `C14` 分支直接关闭 E2EE（`room.rs:1326-1332`）。

**修复建议**
- 把“每次进入都 self_update”改为**由房主/单一协调者做一次 epoch bump**，或使用 server token 里的 seed 作为唯一熵，并在 commit 到达后**重新派生 key 并热更新 LiveKit KeyProvider**（LiveKit 支持 `ratchet_shared_key` / 重新 set key），而不是只在 connect 时设置一次。
- 更简单：语音 E2EE key 不绑定 MLS epoch，而是绑定“房间实例 seed + 固定的频道 key”，并保证同一房间生命周期内不变化；epoch 变化只用于聊天。

### P0-5 房主登录时不会把“已在房间里的成员”加进 MLS 主群

**位置**
- `crates/kaede-client/src/login.rs:249-252`：房主先 `join_room()`。
- `crates/kaede-ui/src/observer.rs:209-261`：只有收到 `PeerJoined` 才触发 `host_add_peer`。
- 服务端 `crates/kaede-server/src/ws.rs:386-409`：房主 `Join` 时只回 `Joined{peers}`，不会为每个已有 peer 再发 `PeerJoined`。

**影响**
- 如果 guest 先在线、host 后登录（或 host 重装丢失 snapshot、重建了群），**这些 guest 永远不会被 Add**。guest 一直处于 `MlsJoining`，发送消息报 “no group”，但 UI 没有明确反馈。
- 首次部署时顺序一旦反了，需要所有 guest 重新登录/重装才能触发新的 `PeerJoined`。

**修复建议**
- 处理 `ClientEvent::Joined` 时，host 对所有 `peers` 逐个执行 `host_add_peer`（带去重/退避）。
- 或者服务端在 host Join 时主动补发每个 peer 的 `PeerJoined`。

## 2. P1 — 高优先级（安全 / 数据一致性 / 主要功能）

### P1-1 私密频道 ≥3 人时群会分裂

**位置**
- `crates/kaede-client/src/connection.rs:1213-1263`：每个收到 `ChannelMemberJoined` 的既有成员都会执行 `channel_add_member`，且只给新人发 Welcome；`:1263` 明确 TODO“commit 广播给其他已有成员（MVP 只有创建者，跳过）”。
- `crates/kaede-server/src/channels.rs:437-451`：服务端把 `ChannelMemberJoined` 广播给**所有**其他成员。

**影响**
- 2 个既有成员会各自 `add_member` 一次 → 产生两个不同的 Commit/Welcome：
  - 新人只接受第一个 Welcome，第二个报 “group already exists”；
  - 两个既有成员各自 merge 了自己的 commit，epoch 不同 → **彼此消息永远解不开**。
- 即使只有创建者在，其他既有成员也收不到 commit，epoch 不一致。

**修复建议**
- 服务端只把 `ChannelMemberJoined` 发给**一个**权威成员（频道创建者/最小 joined_at），或引入“channel group owner”概念。
- 添加成员后，把 Commit 通过 `ChannelSync{0x05}` 广播给其余成员（带宽允许的话），并等待 ack。

### P1-2 Welcome/Commit 不持久化 + `host_add_peer` 幂等短路 → 加人失败不可恢复

**位置**
- `crates/kaede-client/src/room.rs:384-390`：peer 已在 group 就直接 `Ok(())`，不再补发 Welcome。
- `crates/kaede-server/src/ws.rs:509-517`、`crates/kaede-server/src/state.rs:259-269`：Welcome 走 `try_send`，离线/缓冲区满时静默丢弃/返回失败但无重放。
- 服务端没有 MLS Welcome/Commit 的持久化或补投机制。

**影响**
- 一旦 Welcome 在传输中丢失，房主的群状态已经包含该成员；之后每次 `PeerJoined` 都命中幂等短路 → 对方**永久无法入群**，只能通过重建群/清空双方快照恢复。

**修复建议**
- 服务端持久化“待投递 Welcome/Commit”，对方上线后补投（至少对 Welcome 做 store-and-forward）。
- `host_add_peer` 的幂等判断改为“已发送过 Welcome 且收到对端 ack”，或在检测到对端 epoch 落后时重发 Welcome。

### P1-3 op4 可以删除 op5（服主）账号

**位置**
- `crates/kaede-server/src/members.rs:256-270`：`remove_member` 只检查 `is_admin`（op4/op5），不比较目标 rank；而 `update_member` 在 `:159-161` 有“不能动 op5”的保护。

**影响**
- 任意 op4 可以 `DELETE /api/members/{owner}` 删除服主账号，权限体系失效。

**修复建议**
- 删除前读取 target op，要求 `rank(my_op) > rank(target_op)`（op5 不能被任何人删除，或需转移所有权）。
- 同时禁止 op4 删除其他 op4（或允许但需显式策略）。

### P1-4 客户端没有心跳，空闲 5 分钟必被服务器断开，且无自动重连

**位置**
- `crates/kaede-server/src/ws.rs:21`（`WS_IDLE_TIMEOUT = 300s`）、`:259`（超时即 break）。
- 客户端只在测试里发送过 `ClientMessage::Ping`（全仓 grep 无生产调用）。

**影响**
- 用户只要 5 分钟不操作就被断线；UI 只显示 Disconnected，没有重连逻辑，只能重新登录。
- 与 P0-1/P0-3 叠加时体验更差（重登还可能被 P0-3 卡住）。

**修复建议**
- 客户端后台每 30–60s 发 `Ping`（或由 transport 发 WS ping，但服务端目前只把应用层消息计入 idle）。
- UI 增加指数退避自动重连。

### P1-5 附件在 UI 中不可用（401 + 未解密 + 无上传入口）

**位置**
- 服务端 `crates/kaede-server/src/attachments.rs:132-155`：下载必须 `Authorization: Bearer`。
- UI `crates/kaede-ui/src/content.rs:286-309`、`dm_view.rs:138-161`：直接 `<img src="{att.url}">` / `<a href>`，浏览器不会附带 Bearer → 永远 401。
- 客户端已实现 `RoomSession::upload_attachment` / `download_attachment`（`room.rs:919-962`，AES-GCM 包装 `0x04`），但 UI 从未调用；也没有上传 UI。

**影响**
- 即使别的客户端上传了附件，接收端也无法显示/下载；私密频道的加密附件即使能下载也不会被解密。
- 功能实际处于“半成品”状态。

**修复建议**
- UI 下载改为调用 `download_attachment(target_id, id)`，用返回的明文生成 Blob URL；上传走 `upload_attachment`。
- 或者给附件下载增加短时效签名 URL（`?token=`），但注意这是“URL 泄漏即能力”的权衡。

### P1-6 Web 端无法访问独立部署的 API（缺 CORS）

**位置**
- `crates/kaede-server` 没有 `tower-http` / `CorsLayer`（`Cargo.toml` 无相关依赖，`http::router` 无中间件）。
- `crates/kaede-wasm/Dioxus.toml` 也没有代理配置；`HttpApi` 在 wasm 下用浏览器 fetch 直连用户填写的服务器地址。

**影响**
- Web 构建与 signaling server 不同源时，所有 HTTP/WS 请求被浏览器 CORS 拦截；当前仓库也没有由服务器托管 `dist` 的路由，等于 Web 端只能靠外部反代同源部署。

**修复建议**
- 增加 `CorsLayer`（限制允许的 Origin），或明确采用同源反代部署并在文档中写清。

### P1-7 体积上限与 axum 默认 2 MiB body limit 冲突

**位置**
- `crates/kaede-server/src/attachments.rs:27`：`MAX_ATTACHMENT_BYTES = 32 MiB`
- `crates/kaede-server/src/http.rs:444`：消息密文上限 4 MiB
- 未配置 `DefaultBodyLimit`（全仓无匹配），axum 默认 2 MiB。

**影响**
- >2 MiB 的上传/消息在进入 handler 前就被 413 拒绝，代码里的上限形同虚设。

**修复建议**
- 在对应 route 上 `.layer(DefaultBodyLimit::max(MAX_ATTACHMENT_BYTES))`，并对消息接口设置合适上限。

### P1-8 私密频道的元数据被广播给所有人

**位置**
- `crates/kaede-server/src/channels.rs:184-187`（ChannelCreated）、`:248-250`（ChannelUpdated）、`:289`（ChannelDeleted）均使用 `broadcast_all`。
- `Channel` 结构包含 `id/name/is_private/hash_tier`。

**影响**
- 非成员能实时获知私密频道的存在、名称、哈希档位，甚至拿到 id 后由 op3+ 直接 `DELETE /api/channels/{id}`（删除接口不校验成员身份）。
- 与 `list_channels` 的隐藏逻辑（`:69-76`）自相矛盾。

**修复建议**
- 广播按 `channel_members` 过滤；删除/改名私密频道要求是成员或服主。

### P1-9 创建私密频道可被用于 Argon2 内存 DoS

**位置**
- `crates/kaede-server/src/channels.rs:117-133`（hash）与 `:508-517`（`hash_tier=256` 时 256 MiB/次）
- 该路径没有 `login_semaphore`，也没有 `check_rate`。

**影响**
- 任意 op3+ 用户并发创建 `hash_tier=256` 的私密频道即可打出数百 MiB～GB 级峰值内存。

**修复建议**
- 与 login/join 一样走 `login_semaphore` + per-uid rate limit；对 256 档位做单独配额。

### P1-10 私密频道在本地群丢失时会退回主群加密

**位置**
- `crates/kaede-client/src/room.rs:1016-1027`：`if channel_has_group { 0x03 + channel key } else { self.conn.mls_send_app(...) }`
- 服务端 `http.rs:448-467` 只校验 `channel_members`，不校验密文格式。

**影响**
- 私密频道成员在本地群丢失/恢复失败时，发出的消息会用**全服务器共享的主群 key** 加密；任何主群成员都能解密，私密性被静默破坏。
- 接收端 `load_history`（`room.rs:654-660`）对非 `0x03` 密文回退到主群解密，会“看起来正常”。

**修复建议**
- 私密频道在 `channel_has_group == false` 时**拒绝发送**，并提示重新加入；或统一加 `0x05` 标记区分主群密文。

### P1-11 私密频道/反应存在注入与冒充

**位置**
- `crates/kaede-client/src/connection.rs:1170-1211`：`MlsAppMessage` 解密后直接按 payload 的 `c` 字段投递到 UI，未校验发送者是否为该频道的合法成员。
- `crates/kaede-ui/src/observer.rs:318-346`：`apply_reaction` 使用 payload 里的 `r.u` 作为操作者，而不是 MLS 层注入的 `from`。

**影响**
- 任意主群成员可以构造 `c = 某个私密频道 id` 的消息，注入到该频道成员的 UI 列表（显示为“频道内消息”，但不在历史中）。
- 反应列表可以把点赞/表情伪造成任意用户名（UI 层身份冒充）。

**修复建议**
- 消息在 UI 侧必须校验 `p.c` 是否属于当前可访问频道（私密频道还要校验本地 group 存在）。
- 反应的 `u` 一律用 `from` 覆盖（与 `decode_message_payload` 的 C19 修复保持一致）。

## 4. 已核对且**未发现问题**的部分（供参考）

- `kaede-crypto`：AEAD/HKDF/SFrame 实现、AAD 绑定、计数器分区、`checked_next`、sender_id 碰撞检查逻辑正确；HKDF 有 RFC 5869 KAT。
- `kaede-protocol`：CBOR 编解码、16 MiB 上限、方向隔离、`ErrorCode::is_fatal` 分类合理。
- `kaede-mls`：snapshot 读取长度硬上限（防 4GB 分配）、UTF-8 credential 强校验、KP credential 与 uid 校验、sender_id 碰撞拒绝均在位。
- `kaede-server`：SQL 全部参数化（动态 SET 的列名是固定白名单）；附件 id 白名单防路径穿越；附件先写 `.tmp` 再 rename；登录失败锁 
  在 semaphore 之后复查（并发绕过已修）；注册使用 `INSERT ... ON CONFLICT`；`DELETE ... RETURNING` 原子取 KP。
- `kaede-client`：token 不落日志；`fetch_key_package` 双重校验 target + credential；snapshot cipher 按 alg_id 分派；状态机转移约束清晰。
- 构建：check / clippy / test / wasm 均通过；核心 crate clippy 0 warning。
